# Convolution Integration — Prediction Analysis

**Role:** Performance Analyst  
**Active Phase:** Phase 7 — Convolution Integration and End-to-End Dataflow  
**Module:** `convolution_integration`  
**Workflow stage:** Step 3 — `/analyze convolution_integration`  
**Status:** PREDICTION ONLY — no Phase-7 integrated RTL, XSim measurement, synthesis, or implementation result yet.

---

## 1. Scope

This document predicts the performance of the Phase-7 integration architecture before RTL generation.

The integrated transaction is:

```text
external start
 -> control_fsm
 -> memory_interface_dataflow
 -> signed INT32 convolution result
 -> requantize_relu_pipelined
 -> architectural INT8 activation register
 -> external done
```

The analysis derives, from first principles:

- start-to-done latency,
- busy duration,
- minimum legal initiation interval,
- sustained transaction throughput,
- arithmetic work and useful MAC rate,
- memory traffic and bandwidth,
- packed-lane utilization,
- structural resource expectations,
- likely timing-risk locations.

Every number below remains a prediction until the corresponding Phase-7 measurement is performed.

---

## 2. Explicit Assumptions

1. FPGA: XC7A35T-1CPG236C on Basys 3.
2. Clock: 100 MHz.
3. Clock period:

```text
Tclk = 1 / 100,000,000 = 10 ns
```

4. Convolution: 3 x 3, one input channel, one output channel.
5. Useful convolution terms:

```text
3 x 3 x 1 = 9
```

6. Activation and weight values generated by the Phase-6 flow are signed INT8 in `[-127,+127]`.
7. Four activation lanes and four weight lanes are supplied per 32-bit word pair.
8. Three word pairs are required per convolution.
9. Third word uses lane 0 for element 8 and zero-pads lanes 1..3.
10. Activation and weight memories are independent 32-bit read ports.
11. Synchronous memory read latency is one clock.
12. Existing engine start-edge-to-engine-done-edge latency is 4 clock periods = 40 ns.
13. Outer controller remains the five-state Moore FSM.
14. `busy=0` only in `IDLE`; `busy=1` in `LAUNCH`, `WAIT_ENGINE`, `CAPTURE_ACTIVATION`, and `DONE`.
15. Requantizer contains one registered 42-bit product stage.
16. Architectural activation capture occurs after the requantizer's rounding/shift/saturation interval.
17. No physical BRAM is instantiated inside the Phase-7 integration core; memory ports remain external.
18. Requantization parameters are compile-time constants.
19. Representative Phase-6 synthesis mapped the requantizer multiply to one DSP48E1 with `PREG=1`.
20. Existing project evidence indicates the four INT8 engine multipliers map to LUT/carry fabric rather than DSP48 for the current RTL/tool configuration; integrated synthesis must verify this remains true.

## 3. Work Per Transaction

A single 3x3 single-channel output is:

```text
y = sum(i=0..8) a[i] * w[i]
```

Therefore one transaction performs:

```text
9 useful INT8 multiplications
9 useful product contributions to the accumulator
```

If one uses the common convention that one MAC is one multiply plus one accumulation operation, the transaction contains:

```text
9 useful MACs
```

If multiply and addition are counted as separate arithmetic operations, then the same transaction can be described as up to:

```text
9 multiplies + 9 accumulation additions = 18 arithmetic operations
```

This document will use **MAC/s** for the main rate so the counting convention remains explicit.

---

## 4. Packed-Lane Utilization

The engine has four parallel INT8 multiplier lanes and consumes three 32-bit word pairs.

Physical multiplier slots presented across the three words are:

```text
4 lanes/word x 3 words = 12 multiplier slots
```

Useful convolution terms are:

```text
9
```

Therefore useful lane utilization during the three packed word operations is:

```text
9 / 12 = 0.75 = 75%
```

The remaining 25% is caused entirely by the fixed 4-lane packing of the final word:

```text
word 2 = [element8, 0, 0, 0]
```

### Prediction

**Useful packed-lane utilization = 75%.**

This is not a clock-utilization number. It describes how many of the physically presented multiplier lanes contain useful convolution terms.

---

## 5. Start-to-Done Latency Derivation

Use the design convention that `E0` is the rising edge where external `start` is accepted in `IDLE`.

The derived schedule is:

```text
E0: external start accepted; controller enters LAUNCH
E1: engine samples engine_start and requests word 0
E2: memory pipeline advances; request word 1
E3: accumulate word 0; request word 2
E4: accumulate word 1; word 2 becomes available
E5: consume word 2; register final INT32 result and engine_done
E6: controller observes engine_done; requantizer product_reg captures final product
E7: activation_out captures rounded/shifted/saturated q_out; controller enters DONE
```

Elapsed clock intervals from E0 to E7:

```text
E0->E1 = 1
E1->E2 = 2
E2->E3 = 3
E3->E4 = 4
E4->E5 = 5
E5->E6 = 6
E6->E7 = 7
```

Therefore:

```text
latency = 7 cycles
```

At 100 MHz:

```text
latency = 7 x 10 ns = 70 ns
```

### Prediction

**Accepted external start -> valid registered output with external done asserted = 70 ns.**

This is the central prediction that Phase-7 XSim must re-measure.

---

## 6. Busy Duration

The controller is busy in:

```text
LAUNCH
WAIT_ENGINE
CAPTURE_ACTIVATION
DONE
```

From E0 until the transition back to `IDLE` at E8, `busy` remains high.

Therefore:

```text
busy-high duration = E0 -> E8 = 8 cycles
```

At 100 MHz:

```text
8 x 10 ns = 80 ns
```

The difference between latency and busy duration is intentional:

```text
start-to-done latency = 70 ns
busy duration         = 80 ns
```

During the `DONE` interval the output is valid and `done=1`, but `busy` deliberately remains high so a new request cannot yet be accepted.

---

## 7. Minimum Legal Initiation Interval

At E8 the controller enters `IDLE` and `busy` becomes low after the edge.

A legal external source observes `busy=0` during E8->E9 and can present the next one-cycle `start` so it is sampled at E9.

Therefore consecutive accepted starts are separated by:

```text
E0 -> E9 = 9 clock periods
```

At 100 MHz:

```text
initiation interval = 9 x 10 ns = 90 ns
```

This architecture is therefore **not** capable of accepting a new independent convolution every clock. It is a non-overlapped transaction engine.

### Prediction

**Minimum legal accepted-start-to-next-accepted-start interval = 90 ns.**

---

## 8. Sustained Transaction Throughput

With one accepted transaction every 90 ns:

```text
throughput = 1 / 90 ns
           = 1 / (90 x 10^-9 s)
           = 11,111,111.11 transactions/s
```

Equivalent clock-domain derivation:

```text
100,000,000 clocks/s / 9 clocks/transaction
= 11,111,111.11 transactions/s
```

### Prediction

**Maximum sustained acceptance rate = approximately 11.11 million single-output 3x3 transactions/s.**

This is a transaction-interface bound, not a claim about a multi-layer CNN frame rate.

---

## 9. Useful Sustained MAC Rate

Each transaction performs nine useful MAC contributions.

At the predicted sustained transaction rate:

```text
9 MAC/transaction x 11,111,111.11 transactions/s
= 100,000,000 MAC/s
```

Therefore:

```text
sustained useful MAC rate = 100 MMAC/s
```

If, and only if, the convention `1 MAC = 2 arithmetic operations` is used:

```text
100 MMAC/s x 2 = 200 MOPS
```

The MAC/s value is preferred because it avoids ambiguity.

### Important distinction

For one isolated transaction, dividing work by start-to-done latency gives:

```text
9 MAC / 70 ns = 128.57 MMAC/s
```

but this is **not sustained throughput**, because the protocol does not allow the next accepted start immediately at E7. Sustained rate must use the 90 ns initiation interval, giving 100 MMAC/s.

---

## 10. Peak Four-Lane Arithmetic Issue Rate

During a cycle in which a packed word is actually consumed, four multiplier lanes operate in parallel.

At 100 MHz the raw lane capacity during those active word-processing cycles is:

```text
4 multiplications/cycle x 100,000,000 cycles/s
= 400,000,000 multiplier results/s
```

Because only 9 of 12 packed lanes are useful over the three words:

```text
400 Mresults/s x 75% = 300 M useful multiplier results/s
```

This 300 M/s number describes useful density **during the three packed compute words only**. It is not the sustained end-to-end transaction rate. Once launch, memory latency, requantization, DONE, and return-to-IDLE overhead are included, sustained useful MAC rate is the 100 MMAC/s derived above.

## 11. Memory Traffic Per Transaction

Each activation memory word is 32 bits = 4 bytes.

Three activation words require:

```text
3 x 32 bits = 96 bits = 12 bytes
```

Weights are identical:

```text
3 x 32 bits = 96 bits = 12 bytes
```

Combined physical memory traffic per transaction is therefore:

```text
96 + 96 = 192 bits
           = 24 bytes
```

Useful payload is only nine INT8 values from each memory:

```text
activation useful payload = 9 x 8 = 72 bits = 9 bytes
weight useful payload     = 9 x 8 = 72 bits = 9 bytes
combined useful payload   = 144 bits = 18 bytes
```

Packing efficiency:

```text
144 / 192 = 75%
```

### Prediction

Per transaction:

```text
physical reads = 24 bytes total
useful operands = 18 bytes total
packing efficiency = 75%
```

---

## 12. Peak Memory-Port Bandwidth

Each memory has a 32-bit port.

At 100 MHz, maximum raw read-port bandwidth per memory while a read is issued every cycle is:

```text
32 bits/cycle x 100,000,000 cycles/s
= 3.2 x 10^9 bits/s
= 3.2 Gb/s
```

Converting to bytes:

```text
3.2 Gb/s / 8 = 400 MB/s
```

Two independent memories operate in parallel, so combined raw port bandwidth is:

```text
2 x 400 MB/s = 800 MB/s
```

or:

```text
6.4 Gb/s
```

### Prediction

**Peak combined activation+weight read-port bandwidth = 800 MB/s while both ports are actively issuing one 32-bit read per cycle.**

This is a port capability/active-cycle figure, not sustained transaction-average bandwidth.

---

## 13. Sustained Memory Bandwidth at Maximum Transaction Rate

Physical memory traffic per transaction is 24 bytes.

The minimum legal initiation interval is 90 ns.

Therefore sustained physical traffic is:

```text
24 bytes / 90 ns
= 266,666,666.67 bytes/s
= 266.67 MB/s
```

Per memory:

```text
12 bytes / 90 ns = 133.33 MB/s
```

Useful operand traffic is 18 bytes per transaction:

```text
18 bytes / 90 ns = 200 MB/s
```

Per memory useful traffic:

```text
9 bytes / 90 ns = 100 MB/s
```

### Prediction

```text
combined sustained physical read bandwidth = 266.67 MB/s
combined sustained useful operand bandwidth = 200 MB/s
per-memory sustained physical bandwidth = 133.33 MB/s
per-memory sustained useful bandwidth = 100 MB/s
```

The ratio remains:

```text
200 / 266.67 ~= 75%
```

which matches the packing-efficiency derivation.

---

## 14. Why 800 MB/s and 266.67 MB/s Are Both Correct

These two numbers describe different time windows.

`800 MB/s` is the instantaneous combined port rate when both 32-bit memories deliver one word per cycle:

```text
64 bits/cycle x 100 MHz = 6.4 Gb/s = 800 MB/s
```

`266.67 MB/s` is the sustained physical traffic averaged across the complete 90 ns repeated-transaction initiation interval:

```text
24 bytes / transaction / 90 ns = 266.67 MB/s
```

The lower sustained number includes periods in which no new memory word is being requested because the design is launching, finishing accumulation, requantizing, reporting done, or returning to idle.

## 15. Logical Multiplier Count

The integrated arithmetic contains two different multiplier structures.

### Convolution engine

```text
4 parallel INT8 x INT8 multipliers
```

### Requantizer

```text
1 unsigned 18-bit x 24-bit fixed-point multiplier
```

Therefore structural logical multiplier count is:

```text
4 + 1 = 5 multipliers
```

This does **not** imply five DSP48E1 blocks.

Existing project evidence indicates the four small INT8 engine multipliers map to LUT/carry logic under the current RTL/tool settings, while Phase-6 implementation mapped the requantization multiply to one DSP48E1.

### Prediction

```text
logical multipliers = 5
total DSP48E1 expected = 1
```

Integrated synthesis must verify this, because synthesis settings and context can change inference.

## 16. Structural Registered-State Count

This section counts RTL-visible registered bits before synthesis optimization.

### 16.1 `memory_interface_dataflow`

Registered fields are:

```text
state              = 3 bits
accumulator        = 32 bits
result             = 32 bits
done               = 1 bit
activation_rd_en   = 1 bit
activation_addr    = 2 bits
weight_rd_en       = 1 bit
weight_addr        = 2 bits
```

Total:

```text
3 + 32 + 32 + 1 + 1 + 2 + 1 + 2 = 74 bits
```

### 16.2 `control_fsm`

Logical binary state register:

```text
3 bits
```

The Moore outputs are combinational decodes and do not require dedicated RTL output registers.

### 16.3 `requantize_relu_pipelined`

Product pipeline register:

```text
42 bits
```

Phase-6 synthesis showed this can be absorbed into the DSP48E1 output register (`PREG=1`) rather than appearing as 42 Slice FFs.

### 16.4 Architectural output register

```text
activation_out = 8 logical bits
```

Because the legal post-ReLU result is `0..127`, bit 7 is always zero under the current contract and may be optimized to a constant, as happened in the Phase-6 measurement wrapper.

### 16.5 Total logical registered storage

Before synthesis optimization:

```text
74 + 3 + 42 + 8 = 127 registered bits
```

Of these, 42 bits are expected to reside in DSP PREG resources rather than Slice FFs.

Therefore a useful structural view is:

```text
127 total logical registered bits
42 expected in DSP PREG
85 remaining logical register bits before other synthesis optimizations
```

This is **not** a prediction of exactly 85 physical Slice FFs. Vivado may trim redundant sign-extension bits, constant bits, unreachable encodings, or other logic.

## 17. BRAM Prediction

By architectural decision, the Phase-7 integration core does not instantiate physical memories.

Therefore direct resource use of the integration core is predicted as:

```text
internal BRAM = 0
```

This does not mean the final NPU uses no BRAM. A later platform/top-level wrapper is expected to connect the exposed activation and weight memory interfaces to actual FPGA memories.

The distinction is:

```text
Phase-7 core resource report: BRAM expected 0
final board-level design: memory resources must be measured separately
```

---

## 18. Integration-Wrapper Incremental Cost

The wrapper itself adds very little arithmetic logic.

Its unique architectural storage is the final output register:

```text
8 logical FF bits
```

with a possible synthesized implementation of seven physical data FFs plus constant zero for bit 7 under the current ReLU range.

The wrapper also provides wiring among already-existing child blocks. A register enable for `activation_out` may map naturally to FPGA flip-flop clock-enable resources rather than requiring a separate LUT per bit.

Therefore the wrapper's incremental LUT cost is predicted to be very small, but no exact LUT number is claimed before synthesis because optimization and hierarchy flattening can share or remove logic.

## 19. Expected Timing-Critical Regions

The control FSM is shallow and is not expected to dominate timing.

The main candidate paths are structural datapath paths:

### Candidate A — engine compute/accumulation

```text
INT8 multiplication
 -> balanced reduction tree
 -> sign extension
 -> INT32 accumulator input
```

### Candidate B — engine result to requantizer PREG

```text
engine result register
 -> sign/ReLU magnitude preparation
 -> DSP48E1 multiplier
 -> product PREG
```

Phase-6 representative implementation showed this pipelined requantizer stage can meet 100 MHz, but integration can change routing and fanout.

### Candidate C — requantizer PREG to architectural activation register

```text
product PREG
 -> rounding addition
 -> fixed shift
 -> saturation
 -> activation_out register
```

### Prediction

The 100 MHz target is architecturally plausible because the requantizer was specifically pipelined to break its former long path, but **integrated timing closure is not proven** until post-implementation timing is run on the Phase-7 core.

No Fmax prediction is made from unit-level slack alone.

## 20. Latency vs Throughput Summary

These metrics must not be confused:

```text
start-to-done latency = 7 cycles = 70 ns
busy-high duration    = 8 cycles = 80 ns
initiation interval   = 9 cycles = 90 ns
```

Therefore:

```text
one isolated result appears after 70 ns
controller is still busy through 80 ns
next legal start is accepted after 90 ns
```

This is why sustained throughput is based on 90 ns rather than 70 ns.

## 22. What Step 8 Must Measure

The following predictions must later be compared against integrated evidence:

1. accepted `start` to `done` = 7 cycles / 70 ns,
2. `busy` high duration = 8 cycles / 80 ns,
3. earliest next legal accepted `start` = 9 cycles / 90 ns,
4. exactly three activation addresses and three weight addresses per transaction,
5. address sequence `0 -> 1 -> 2`,
6. exactly 24 physical memory bytes consumed per transaction,
7. output capture occurs at E7 rather than E6,
8. no previous-transaction value leaks into `activation_out`,
9. integrated synthesis DSP count,
10. integrated LUT/FF/CARRY resource count,
11. integrated post-route setup and hold timing at 100 MHz.

Only after those measurements exist should this file be updated with a measured-vs-predicted section.

## 23. Analysis Gate

Before proceeding to Step 4 and then RTL generation, the learner must explain in their own words:

1. Why latency is 70 ns but the minimum initiation interval is 90 ns.
2. Why sustained throughput is `100 MHz / 9`, not `100 MHz / 7`.
3. Why the memory system has an 800 MB/s peak combined port rate but only 266.67 MB/s sustained physical traffic for repeated transactions.
4. Why four MAC lanes achieve only 75% useful lane utilization for a 3x3 single-channel convolution.
5. Why the structural design contains 127 logical registered bits but we must not predict exactly 127 Slice FFs.
6. Why the expected integrated DSP count is one even though the RTL contains five logical multipliers.
