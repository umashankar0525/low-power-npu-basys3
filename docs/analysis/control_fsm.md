# Control FSM — Performance Analysis and Prediction

**Project:** Low-Power INT8 NPU on Basys 3  
**Role:** Performance Analyst  
**Active Phase:** Phase 1 — Arithmetic Foundations and MAC Design  
**Module:** Control FSM  
**Workflow stage:** ANALYZE / PREDICT  
**Status:** Prediction only; no RTL, simulation, or synthesis measurement yet for this controller.

## 1. Scope

This analysis derives the expected state width, control latency, whole-transaction latency, throughput implications, and control-resource cost for the proposed five-state supervisory FSM.

The FSM does not reimplement BRAM addressing or MAC sequencing. It treats `memory_interface_dataflow` as a self-contained convolution engine with a `start`/`done` transaction interface.

## 2. Assumptions

- FPGA: XC7A35T-1CPG236C on Basys 3.
- Clock: 100 MHz.
- Clock period: `1 / 100 MHz = 10 ns`.
- Reset: synchronous, active high.
- External `start` is a one-cycle pulse and is only guaranteed to be accepted in `IDLE`.
- Supervisory states are `IDLE`, `LAUNCH`, `WAIT_ENGINE`, `CAPTURE_ACTIVATION`, and `DONE`.
- Moore-style outputs are derived from the current state.
- `engine_start` is high only in `LAUNCH`.
- `capture_activation` is high only in `CAPTURE_ACTIVATION`.
- `done` is high only in `DONE`.
- `busy` is high in `LAUNCH`, `WAIT_ENGINE`, and `CAPTURE_ACTIVATION`.
- The existing convolution engine has measured start-edge-to-done-edge latency of 40 ns at 100 MHz, equal to four clock periods.
- `engine_done` is generated by sequential logic in the convolution engine as a one-cycle pulse.
- `relu_activation` is combinational and contributes zero architectural clock cycles.
- The final INT8 activation is captured in a register when `capture_activation = 1`.
- Separate synchronous modules observe one another's registered outputs on the following active clock edge; nonblocking assignments do not become visible to another sequential block during the same edge.

## 3. Minimum State-Register Width

There are five supervisory states.

A binary state register with `N` bits can represent `2^N` states.

Check two bits:

`2^2 = 4`

Four encodings are insufficient for five states.

Check three bits:

`2^3 = 8`

Eight encodings are sufficient.

Therefore the minimum binary state width is:

`ceil(log2(5)) = 3 bits`

### Prediction

- Minimum logical state storage: **3 flip-flops** with binary encoding.
- Vivado may choose a different FSM encoding during synthesis, such as one-hot, unless encoding is constrained. In that case the physical state-register FF count can differ from the logical minimum.

## 4. Existing Convolution-Engine Latency

The already-verified `memory_interface_dataflow` engine uses one-cycle synchronous memory and requires three packed words.

Its measured timeline is:

| Engine edge | Action |
|---|---|
| E0 | Accept engine `start`; request word 0 |
| E1 | Request word 1; word 0 becomes available |
| E2 | Accumulate word 0; request word 2 |
| E3 | Accumulate word 1 |
| E4 | Form final result from word 2; assert `engine_done` |

The elapsed time from E0 to E4 is:

`4 clock periods`

At 10 ns per period:

`4 x 10 ns = 40 ns`

This 40 ns is the measured engine latency that the supervisory controller wraps around.

## 5. Supervisory Timing Derivation

Let `S0` be the clock edge at which the external `start` pulse is accepted while the supervisory controller is in `IDLE`.

### Edge S0 — accept external start

Before S0:

- current state = `IDLE`
- external `start = 1`

At S0 the state register transitions to `LAUNCH`.

During the interval S0 -> S1:

- `engine_start = 1`
- `busy = 1`

The convolution engine has not yet sampled that newly asserted `engine_start`; it samples it at S1.

### Edge S1 — engine accepts start

At S1:

- the convolution engine sees `engine_start = 1` and begins its transaction,
- the supervisory FSM transitions from `LAUNCH` to `WAIT_ENGINE`.

The engine now requires four clock periods from S1 to its completion edge.

Therefore the engine completion edge is:

`S1 + 4 periods = S5`

### Edge S5 — engine internally asserts done

At S5 the convolution engine executes its final sequential state and schedules:

- final INT32 result update,
- `engine_done <= 1`.

Because both the engine and the supervisory controller are synchronous sequential logic, the supervisory controller cannot use the newly updated `engine_done` value during the same edge S5. It still sees the previous value.

During S5 -> S6:

- `engine_done = 1`,
- final INT32 `engine_result` is stable,
- combinational ReLU output propagates from that result.

### Edge S6 — supervisory FSM observes engine_done

At S6 the supervisory FSM sees `engine_done = 1` and transitions:

`WAIT_ENGINE -> CAPTURE_ACTIVATION`

During S6 -> S7:

- `capture_activation = 1`,
- `busy = 1`.

The ReLU result is already combinationally derived from the stable engine result.

### Edge S7 — capture final activation and enter DONE

At S7 the surrounding output register sees `capture_activation = 1` and captures the INT8 ReLU result.

The supervisory FSM simultaneously transitions:

`CAPTURE_ACTIVATION -> DONE`

After S7:

- the registered INT8 output is valid,
- `done = 1`,
- `busy = 0`.

## 6. Total External Start-to-Done Latency

The elapsed clock periods are:

1. S0 -> S1: external-start acceptance to engine-start acceptance.
2. S1 -> S2: engine period 1.
3. S2 -> S3: engine period 2.
4. S3 -> S4: engine period 3.
5. S4 -> S5: engine period 4; engine result/done generated.
6. S5 -> S6: supervisory controller waits one edge to observe registered `engine_done`.
7. S6 -> S7: activation-capture state; output is registered at S7.

Therefore:

`Total latency = 7 clock periods`

At 100 MHz:

`7 x 10 ns = 70 ns`

### Prediction

**External accepted-start edge -> external done/output-valid edge = 70 ns.**

This is a prediction based on the proposed Moore-style supervisory state machine and the already-measured 40 ns internal engine latency.

## 7. Where the 30 ns Supervisory Overhead Comes From

The wrapped engine itself takes 40 ns from its own accepted start to its own done edge.

The full supervisory transaction is predicted as 70 ns.

Therefore added latency is:

`70 ns - 40 ns = 30 ns`

or:

`3 clock periods`

Those three periods are not arbitrary:

1. **Launch period** — external request is converted into a clean one-cycle internal engine-start pulse.
2. **Done-observation period** — a registered `engine_done` generated at the engine edge is observed by the outer FSM on the next edge.
3. **Activation-capture period** — the combinational ReLU result is captured into a final output register before external `done` is asserted.

The architecture intentionally spends these cycles to create clean hierarchical and synchronous boundaries.

## 8. Busy Duration

`busy = 1` in:

- `LAUNCH`,
- every cycle spent in `WAIT_ENGINE`,
- `CAPTURE_ACTIVATION`.

From S0 through just before S7, the transaction is active.

Therefore predicted busy-high duration is:

`7 clock periods = 70 ns`

At S7 the controller enters `DONE`, where the current design defines:

- `busy = 0`,
- `done = 1`.

## 9. Pulse Activity

For each successful transaction:

- `engine_start` is high for exactly one clock interval.
- `capture_activation` is high for exactly one clock interval.
- `done` is high for exactly one clock interval.

This low toggle count is favorable for control-path dynamic power, although the arithmetic datapath will dominate switching during actual convolution work.

## 10. Back-to-Back Transaction Limitation

The current state sequence after S7 is:

`DONE -> IDLE`

A `start` request is only sampled in `IDLE`.

At the edge that leaves `DONE`, the pre-edge current state is still `DONE`, so a new start pulse presented only at that edge would not be accepted.

Therefore one full `IDLE` interval is required before the next start can be sampled.

Timeline after first transaction:

- S7: enter `DONE`.
- S8: leave `DONE`, enter `IDLE`.
- S9: earliest edge at which a new `start` can be accepted.

Thus earliest accepted-start to next accepted-start interval is:

`S0 -> S9 = 9 clock periods`

At 100 MHz:

`9 x 10 ns = 90 ns`

Maximum non-overlapped transaction-acceptance rate under this handshake is therefore:

`100,000,000 / 9`

`= 11,111,111.11 transactions/s`

This is a controller-level bound for repeated isolated 3x3 transactions, not a claim for a future multi-pixel convolution engine.

## 11. Handshake Risk Identified During Analysis

The proposed design defines `busy = 0` in `DONE`, but `start` is only accepted in `IDLE`.

That creates a subtle interface condition:

- external logic may see `busy = 0` during `DONE`,
- external logic may reasonably assume the controller is ready,
- but a one-cycle `start` pulse during `DONE` would be ignored.

Therefore `busy = 0` is not identical to `ready = 1` in the current design.

Before RTL generation, one of the following interface policies should be chosen explicitly:

1. Keep the current design and document that `start` is legal only in `IDLE`; the source must not use `busy` alone as a ready signal.
2. Keep `busy = 1` through `DONE`, making `busy = 0` correspond more closely to idle readiness.
3. Add an explicit `ready` signal that is high only in `IDLE`.
4. Allow `DONE` to accept a new start directly, reducing restart overhead.

No change is made in this analysis step; this is an architectural issue discovered by first-principles timing analysis and must be resolved before RTL is finalized.

## 12. Control Resource Prediction

### State flip-flops

Binary minimum:

`ceil(log2(5)) = 3 FFs`

### Output registers

For a pure Moore combinational-output implementation, the four control outputs do not inherently require dedicated output FFs.

The final INT8 activation register is part of integration/output datapath rather than the FSM state itself and requires:

`8 FFs`

if implemented as one 8-bit registered output.

### LUT model

With binary state encoding, the controller has:

- three next-state bits,
- four Moore control outputs: `engine_start`, `capture_activation`, `busy`, `done`.

That is seven Boolean output functions.

The next-state logic depends on at most:

- 3 state bits,
- `start`,
- `engine_done`,

for a total of five logical inputs.

An Artix-7 LUT6 can implement one arbitrary Boolean function of up to six inputs. Therefore, as a first-order structural model, each next-state bit can fit in one LUT6, and each control-output decode can also fit in one LUT6.

A conservative simple binary-encoding model is therefore approximately:

`3 next-state LUTs + 4 output-decode LUTs = 7 LUTs`

This is **not** a guaranteed post-synthesis LUT count. Vivado may share logic, remove logic, or re-encode the FSM, so measured LUT usage may be lower or higher.

## 13. DSP and BRAM Prediction

The supervisory FSM performs no multiplication and stores no bulk data.

Therefore its direct resource requirement is predicted as:

- DSP48: **0**
- BRAM: **0**

The convolution engine still owns the arithmetic and memory resources.

## 14. Timing Prediction at 100 MHz

The 100 MHz target gives:

`Tclk = 10 ns`

The supervisory control path contains no multiplier, adder tree, or 32-bit accumulator.

The important synchronous control paths are conceptually:

`state register -> next-state decode -> state register`

and

`engine_done/start -> next-state decode -> state register`

Under binary encoding, the relevant Boolean logic depends on no more than five logical inputs and can in principle map into one LUT6 level per next-state bit.

Therefore the supervisory FSM is predicted to have substantial timing margin relative to 10 ns and is unlikely to be the system critical path.

However, actual timing must be measured after synthesis/implementation. Routing delay, FSM re-encoding, fanout, and integration placement can change the result.

The arithmetic engine's multiplier/reduction/accumulator paths remain more plausible critical-path candidates than this simple controller.

## 15. Predicted Transaction Timeline Summary

| Interval / edge | Supervisory state/action | Engine action |
|---|---|---|
| S0 | external `start` accepted; enter `LAUNCH` | idle |
| S0 -> S1 | `engine_start = 1` | waiting to sample start |
| S1 | enter `WAIT_ENGINE` | accepts start |
| S1 -> S5 | wait | BRAM/MAC/accumulation transaction |
| S5 | still `WAIT_ENGINE` | final INT32 result and `engine_done` generated |
| S5 -> S6 | wait one cycle for registered handshake visibility | result stable; ReLU propagates |
| S6 | enter `CAPTURE_ACTIVATION` | idle after completed transaction |
| S6 -> S7 | `capture_activation = 1` | result remains stable |
| S7 | output register captures INT8 result; enter `DONE` | idle |
| S7 -> S8 | `done = 1`, `busy = 0` | idle |
| S8 | return to `IDLE` | idle |
| S9 | earliest next one-cycle `start` can be sampled under current contract | new transaction may begin |

## 17. Hard Gate Before RTL

Before RTL generation, the user must confirm understanding of:

1. Why the five-state supervisory FSM needs at least three binary state bits.
2. Why the measured 40 ns convolution engine becomes a predicted 70 ns external transaction when wrapped by the current supervisory FSM.
3. Why the outer FSM cannot observe a newly registered `engine_done` on the same clock edge that the engine asserts it.
4. Why `CAPTURE_ACTIVATION` adds one deliberate clock period even though ReLU itself is combinational.
5. Why `busy = 0` in `DONE` creates a handshake ambiguity if external logic interprets `busy = 0` as immediate readiness for a new start.

No Control-FSM RTL is generated until this prediction and handshake policy are understood and the handshake ambiguity is resolved.
