# Control FSM — Performance Analysis and Prediction

**Project:** Low-Power INT8 NPU on Basys 3  
**Role:** Performance Analyst  
**Active Phase:** Phase 1 — Arithmetic Foundations and MAC Design  
**Module:** Control FSM  
**Workflow stage:** ANALYZE / PREDICT  
**Status:** Prediction finalized before RTL verification.

## 1. Scope

This analysis derives the expected state width, control latency, whole-transaction latency, throughput implications, and control-resource cost for the finalized five-state supervisory FSM.

The FSM does not reimplement BRAM addressing or MAC sequencing. It treats `memory_interface_dataflow` as a self-contained convolution engine with a `start`/`done` transaction interface.

## 2. Assumptions

- FPGA: XC7A35T-1CPG236C on Basys 3.
- Clock: 100 MHz.
- Clock period: `1 / 100 MHz = 10 ns`.
- Reset: synchronous, active high.
- External `start` is a one-cycle pulse.
- External `start` is legal only when `busy = 0`.
- Supervisory states: `IDLE`, `LAUNCH`, `WAIT_ENGINE`, `CAPTURE_ACTIVATION`, `DONE`.
- Moore-style outputs depend on current state.
- `engine_start` is high only in `LAUNCH`.
- `capture_activation` is high only in `CAPTURE_ACTIVATION`.
- `done` is high only in `DONE`.
- `busy` is high in every state except `IDLE`, including `DONE`.
- The existing convolution engine has measured start-edge-to-done-edge latency of 40 ns at 100 MHz, equal to four clock periods.
- `engine_done` is generated by sequential logic as a one-cycle pulse.
- `relu_activation` is combinational and contributes zero architectural clock cycles.
- The final INT8 activation is captured in a register when `capture_activation = 1`.
- Separate synchronous sequential blocks observe newly registered values on the following active edge because nonblocking assignments update after right-hand-side evaluation at the current edge.

## 3. Minimum State-Register Width

There are five states.

A binary state register with `N` bits represents `2^N` unique encodings.

For two bits:

`2^2 = 4`

Four encodings are insufficient.

For three bits:

`2^3 = 8`

Eight encodings are sufficient.

Therefore:

`ceil(log2(5)) = 3 bits`

### Prediction

The logical minimum state storage is **3 flip-flops** using binary encoding.

Vivado may choose a different physical FSM encoding unless constrained, so post-synthesis FF count may differ.

## 4. Existing Convolution-Engine Latency

The already-verified convolution engine uses three packed memory words and one-cycle synchronous-memory behavior.

Its measured sequence is:

| Engine edge | Action |
|---|---|
| E0 | Accept engine `start`; request word 0 |
| E1 | Request word 1; word 0 becomes available |
| E2 | Accumulate word 0; request word 2 |
| E3 | Accumulate word 1 |
| E4 | Form final result from word 2; assert `engine_done` |

Elapsed time:

`E0 -> E4 = 4 clock periods`

At 10 ns per period:

`4 x 10 ns = 40 ns`

This 40 ns is the measured internal-engine latency that the supervisory FSM wraps around.

## 5. Supervisory Timing Derivation

Let `S0` be the edge where the external `start` pulse is accepted while the controller is in `IDLE`.

### S0 — accept external start

Before the edge:

- state = `IDLE`
- `start = 1`

At S0 the controller enters `LAUNCH`.

During S0 -> S1:

- `engine_start = 1`
- `busy = 1`

The inner engine samples that launch pulse at S1.

### S1 — engine accepts start

At S1:

- the inner engine begins its transaction,
- the outer FSM enters `WAIT_ENGINE`.

The inner engine requires four periods, so its completion edge is:

`S1 + 4 periods = S5`

### S5 — engine creates result and done

At S5 the engine's final sequential state schedules:

- updated final INT32 result,
- `engine_done <= 1`.

The outer FSM cannot use that newly updated `engine_done` during the same S5 edge because both modules evaluate their sequential right-hand sides before nonblocking assignments become visible.

During S5 -> S6:

- `engine_done = 1`,
- `engine_result` is stable,
- the combinational ReLU output propagates from `engine_result`.

### S6 — outer FSM observes engine_done

At S6 the outer controller sees `engine_done = 1` and transitions:

`WAIT_ENGINE -> CAPTURE_ACTIVATION`

During S6 -> S7:

- `capture_activation = 1`,
- `busy = 1`,
- the ReLU output is stable from the completed engine result.

### S7 — capture final activation and enter DONE

At S7 the surrounding final-output register captures the INT8 ReLU value.

The FSM enters `DONE`.

During S7 -> S8:

- registered INT8 output is valid,
- `done = 1`,
- `busy = 1`.

Keeping `busy` high here is intentional: the controller is not ready to accept a new request while it is still in `DONE`.

### S8 — return to IDLE

At S8 the FSM enters `IDLE`.

After S8:

- `done = 0`,
- `busy = 0`,
- the controller is genuinely ready for another external `start`.

## 6. External Start-to-Done Latency

The elapsed periods from accepted external start to output-valid/done are:

1. S0 -> S1: supervisory launch period.
2. S1 -> S2: engine period 1.
3. S2 -> S3: engine period 2.
4. S3 -> S4: engine period 3.
5. S4 -> S5: engine period 4; engine produces result/done.
6. S5 -> S6: outer FSM waits one edge to observe registered `engine_done`.
7. S6 -> S7: activation-capture period.

Therefore:

`Total latency = 7 clock periods`

At 100 MHz:

`7 x 10 ns = 70 ns`

### Prediction

**Accepted external `start` edge -> registered final INT8 output valid and external `done` asserted = 70 ns.**

## 7. Why Supervisory Overhead Is Three Cycles

The inner engine itself takes 40 ns.

The full transaction takes 70 ns.

Therefore:

`70 ns - 40 ns = 30 ns`

or three periods.

Those three periods come from:

1. **Launch** — convert external request into a clean one-cycle `engine_start` pulse.
2. **Registered done visibility** — the outer FSM sees the engine's newly registered `engine_done` on the following edge.
3. **Activation capture** — register the combinational ReLU result before reporting external completion.

These are deliberate synchronous boundaries, not unexplained idle cycles.

## 8. Busy Duration After Final Handshake Decision

Final policy:

```text
busy = 0 only in IDLE
busy = 1 in LAUNCH, WAIT_ENGINE, CAPTURE_ACTIVATION, and DONE
```

From S0 until S8, `busy` remains high.

Therefore:

`busy-high duration = 8 clock periods`

At 100 MHz:

`8 x 10 ns = 80 ns`

This is longer than start-to-done latency because `done` is asserted during the one-cycle `DONE` interval while `busy` deliberately remains high.

This cleanly separates two meanings:

- `done = 1` means the completed output is valid now.
- `busy = 0` means a new request may now be issued.

## 9. Back-to-Back Request Timing

The controller returns to `IDLE` at S8. An external source that obeys the interface sees `busy = 0` during S8 -> S9 and may assert a one-cycle `start` during that interval.

The earliest next accepted start is therefore S9.

So accepted-start to next accepted-start interval is:

`S0 -> S9 = 9 clock periods`

At 100 MHz:

`9 x 10 ns = 90 ns`

Maximum repeated transaction acceptance rate for this simple non-overlapped handshake is:

`100,000,000 / 9 = 11,111,111.11 transactions/s`

This is only a controller-level bound for repeated single 3x3 transactions. It is not a throughput claim for a future multi-window convolution engine.

## 10. Pulse Activity

Per successful transaction:

- `engine_start`: high for one cycle.
- `capture_activation`: high for one cycle.
- `done`: high for one cycle.

`busy` changes only at transaction entry and final return to idle.

The supervisory control network therefore has low expected toggle activity relative to the arithmetic datapath.

## 11. Control Resource Prediction

### State register

Binary logical minimum:

`3 FFs`

### Direct datapath storage

The FSM itself does not store arithmetic data.

The final 8-bit activation register belongs to the surrounding integration/output datapath, requiring 8 FFs when implemented.

### Next-state and output logic

The next-state logic depends on:

- 3 state bits,
- `start`,
- `engine_done`.

That is at most five logical inputs.

An Artix-7 LUT6 can implement an arbitrary Boolean function of up to six inputs. Therefore each binary next-state bit can structurally fit in one LUT6.

There are three next-state bits.

The four Moore outputs are:

- `engine_start`,
- `capture_activation`,
- `busy`,
- `done`.

A conservative first-order model is therefore:

`3 next-state functions + 4 output decode functions = about 7 LUT6-equivalent functions`

This is a prediction, not a guaranteed synthesis result. Vivado may share decode logic, change state encoding, or otherwise optimize the structure.

## 12. DSP and BRAM Prediction

The supervisory controller performs no multiplication and stores no bulk data.

Predicted direct resource requirement:

- DSP48: **0**
- BRAM: **0**

The inner convolution engine continues to own arithmetic and memory resources.

## 13. Timing Prediction at 100 MHz

Clock period:

`10 ns`

The supervisory control path contains no multiplier, adder tree, or 32-bit accumulation path.

Typical synchronous paths are:

```text
state FF -> decode -> state FF
start/engine_done -> decode -> state FF
```

With only three state bits and two condition inputs, the control logic is shallow. Therefore the FSM is predicted to have comfortable timing margin at 100 MHz and is unlikely to become the system critical path.

Actual timing must still be measured after synthesis/implementation because routing, fanout, and synthesis encoding decisions can change the result.

## 14. Final Predicted Timeline

| Edge/interval | Supervisory behavior | Engine behavior |
|---|---|---|
| S0 | accept external start; enter `LAUNCH` | idle |
| S0 -> S1 | `engine_start=1`, `busy=1` | waiting to sample start |
| S1 | enter `WAIT_ENGINE` | accepts start |
| S1 -> S5 | wait, `busy=1` | BRAM/MAC/accumulation transaction |
| S5 | outer still sees old done | final result and `engine_done` generated |
| S5 -> S6 | `busy=1` | result stable, ReLU propagates |
| S6 | enter `CAPTURE_ACTIVATION` | idle |
| S6 -> S7 | `capture_activation=1`, `busy=1` | result stable |
| S7 | final INT8 output captured; enter `DONE` | idle |
| S7 -> S8 | `done=1`, `busy=1` | idle |
| S8 | enter `IDLE`; `busy=0` | idle |
| S9 | earliest next accepted one-cycle start | new transaction may begin |

## 16. Resolved Handshake Issue

An earlier draft allowed `busy = 0` during `DONE` even though `start` was accepted only in `IDLE`. That could falsely advertise readiness.

The user explicitly agreed to the corrected policy:

```text
busy remains high in DONE
busy becomes low only after the controller reaches IDLE
```

The handshake ambiguity is therefore resolved before RTL generation.

## 17. RTL Gate

The user confirmed understanding that:

1. the 40 ns inner engine becomes 70 ns externally because the supervisory FSM adds three periods,
2. the outer FSM sees a newly registered `engine_done` on the following clock edge,
3. `busy` should remain high through `DONE` and become low only in `IDLE`.

Therefore the analysis/prediction gate is complete and Control-FSM RTL generation is permitted.
