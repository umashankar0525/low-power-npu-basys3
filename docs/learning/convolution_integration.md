# Phase 7 — Convolution Integration and End-to-End Dataflow

**Role:** Teaching Assistant  
**Active Phase:** Phase 7 — Convolution Integration and End-to-End Dataflow  
**Module:** `convolution_integration`  
**Workflow stage:** Step 1 — `/teach convolution_integration`  

---

## 1. Purpose of Phase 7

Phase 6 established that the quantized arithmetic path is numerically correct and that the timing-refined requantizer can meet the 100 MHz target for the representative configuration. Phase 7 changes the problem from **“does each block work?”** to **“do the blocks work together with the correct cycle-to-cycle contract?”**

This distinction is fundamental in digital hardware. A multiplier may be correct, a memory interface may be correct, a controller may be correct, and a requantizer may be correct, while the complete system can still fail because one block samples another block one cycle too early or too late.

The purpose of this phase is therefore to integrate the already-built pieces into one coherent convolution transaction:

```text
external start
    -> supervisory control FSM
    -> memory/dataflow convolution engine
    -> signed INT32 convolution result
    -> pipelined ReLU + requantization
    -> activation capture register
    -> external done
```

The first integration target is **one complete 3x3, one-input-channel, one-output-channel convolution transaction**. We are not yet building a general multi-layer neural-network accelerator.

---

## 2. Assumptions

The following assumptions are explicit and must remain true unless a later design step changes them.

1. FPGA target: Basys 3, XC7A35T-1CPG236C.
2. Clock frequency: 100 MHz.
3. Clock period:

```text
Tclk = 1 / 100 MHz = 10 ns
```

4. Reset is synchronous and active high in the current controller/dataflow/requantizer blocks.
5. Convolution kernel: 3x3.
6. Input channels: 1.
7. Output channels for the present integration transaction: 1.
8. Quantized activation and weight range generated by the Phase-6 flow: `[-127,+127]`.
9. Nine signed INT8 products contribute to one convolution result.
10. The memory/dataflow block assumes synchronous memory with one clock of read latency.
11. Four INT8 values are packed into each 32-bit memory word.
12. Word 2 contains the ninth INT8 value in lane 0 and zeroes in lanes 1..3.
13. The convolution engine produces a signed 32-bit result and a one-cycle `done` pulse.
14. The requantizer contains one pipeline register after its multiply.
15. The architectural activation register is outside the requantizer and captures its combinational `q_out` on a later clock edge.
16. The currently discussed 70 ns start-to-done latency is a **prediction from cycle scheduling** until Phase-7 integrated simulation measures it.

## 3. What already exists in the repository

The relevant current RTL is divided into three responsibilities.

### 3.1 Memory/dataflow convolution engine

`rtl/compute/memory_interface_dataflow.v` already performs one complete 3x3 integer dot product from three packed activation words and three packed weight words.

Its interface includes:

```text
start
activation_rd_en / activation_addr / activation_data
weight_rd_en     / weight_addr     / weight_data
result
 done
```

Internally it unpacks four signed INT8 lanes from each 32-bit word, computes four INT8 x INT8 products, reduces those products with a balanced adder tree, and accumulates the three word-level partial sums into an INT32 result.

The three useful memory groups are:

```text
word 0 -> elements 0,1,2,3
word 1 -> elements 4,5,6,7
word 2 -> element 8 + three zero lanes
```

Thus the hardware performs twelve lane multiplies physically across three words, but three of the final four multiplications are by zero. The mathematical convolution still contains exactly nine meaningful products.

### 3.2 Supervisory control FSM

`rtl/control/control_fsm.v` is not the arithmetic engine. Its job is transaction sequencing.

Its important signals are:

```text
external start
engine_start
engine_done
capture_activation
busy
external done
```

Its states are:

```text
IDLE
LAUNCH
WAIT_ENGINE
CAPTURE_ACTIVATION
DONE
```

This controller therefore answers a different question from the dataflow engine:

- the engine knows **how to calculate** the convolution,
- the controller knows **when to launch, wait, capture, and finish**.

Keeping these responsibilities separate is good hardware architecture because arithmetic and control can be reasoned about independently.

### 3.3 Pipelined requantizer

`rtl/activation/requantize_relu_pipelined.v` performs:

```text
INT32 accumulator
 -> ReLU/sign gate
 -> 18-bit positive magnitude
 -> 18 x 24 fixed-point multiply
 -> 42-bit product register
 -> rounding
 -> right shift
 -> saturation
 -> INT8 q_out
```

The important integration fact is that `q_out` is not generated directly from the current `acc_in`. It is generated from the **registered product**.

That means the convolution result must remain valid long enough to be sampled into the requantizer's product register, and the final INT8 value must then be captured on a later edge.

## 4. Integration is fundamentally a timing problem

It is tempting to think top-level integration means only connecting ports:

```text
engine.result -> requantizer.acc_in
engine.done   -> controller.engine_done
controller.engine_start -> engine.start
```

Those connections are necessary, but they are not sufficient.

The important question is:

> On which clock edge does each producer update its output, and on which later edge does each consumer actually sample that output?

All three major blocks are synchronous. Nonblocking assignments update registers only after the active clock-edge evaluation. Therefore, if two `always @(posedge clk)` blocks run on the same edge, the consumer sees the producer's **old registered value** during that edge.

This is why cycle-level reasoning is required before writing the Phase-7 integration RTL.

---

## 5. The engine's internal memory schedule

The memory/dataflow engine uses these states:

```text
ST_IDLE
ST_WAIT0
ST_WORD0
ST_WORD1
ST_WORD2
```

The synchronous-memory assumption creates the first waiting cycle.

### Engine launch

When `start` is accepted in `ST_IDLE`, the engine:

```text
clears the accumulator
requests activation word 0
requests weight word 0
moves to ST_WAIT0
```

Because memory is assumed to have one-clock read latency, word 0 cannot be accumulated immediately.

### WAIT0

During `ST_WAIT0`, the engine requests word 1. Word 0 becomes available for the next computation cycle.

### WORD0

The engine consumes word 0 and accumulates:

```text
S0 = p0 + p1 + p2 + p3
```

At the same time, it requests word 2.

### WORD1

The engine consumes word 1 and accumulates:

```text
S1 = p4 + p5 + p6 + p7
```

### WORD2

The final packed word represents:

```text
[element8, 0, 0, 0]
```

so its partial sum is simply the ninth product mathematically:

```text
S2 = p8
```

The final result is therefore:

```text
result = S0 + S1 + S2
```

which is exactly:

```text
result = sum(i=0..8) activation[i] * weight[i]
```

At the end of `ST_WORD2`, the engine registers both the final `result` and `done = 1`.

---

## 6. Why `engine_done` and `result` are not instantly visible to the outer FSM

Suppose the child engine is in `ST_WORD2` just before a rising edge.

At that edge it executes conceptually:

```text
result <= final_sum
done   <= 1
```

Because these are nonblocking assignments, the outer controller's state logic evaluating on the **same edge** still sees the engine's old registered `done` value.

Therefore the outer FSM does not respond to the new `engine_done = 1` until the next edge.

This one-cycle observation delay is not a bug. It is normal synchronous behavior.

It is also useful here, because it gives the pipelined requantizer time to sample the newly registered convolution result.

---

## 7. Interaction with the requantizer pipeline

The requantizer has a register:

```text
product_reg <= positive_accumulator_magnitude * M_INT
```

Consider the edge on which the convolution engine registers the final result.

At that exact edge, the requantizer still sees the engine's **old** `result`, so it cannot yet capture the final convolution product.

After the edge, the engine's `result` contains the correct final INT32 value.

On the **next** edge, the requantizer samples that final result and stores its 42-bit fixed-point product in `product_reg`.

After that second edge, the stage-2 combinational logic produces the correct rounded, shifted, saturated INT8 `q_out`.

Therefore the correct ordering is:

```text
edge N:
    engine registers final INT32 result

edge N+1:
    requantizer product register captures product of final result

between N+1 and N+2:
    rounding / shift / saturation produce valid q_out

edge N+2:
    architectural activation register captures q_out
```

This is the most important Phase-7 timing relationship.

---

## 8. Why the existing supervisory FSM can align with the pipeline

The current controller waits for `engine_done` in `ST_WAIT_ENGINE`.

When the engine asserts `done`, the controller cannot transition based on the newly registered pulse until the following edge. At that following edge:

1. the controller moves into `ST_CAPTURE_ACTIVATION`, and
2. the requantizer captures the final engine result into `product_reg`.

During the new `ST_CAPTURE_ACTIVATION` cycle, the requantizer's stage-2 combinational output becomes valid.

At the next edge, an activation output register controlled by `capture_activation` can capture that valid `q_out`.

This means the pipeline stage can fit into the existing supervisory schedule without automatically requiring another FSM state.

However, this is still a **design hypothesis** until the integrated RTL and waveform prove the exact edge relationships.

That distinction matters:

```text
cycle schedule derived on paper -> prediction
integrated XSim waveform         -> measurement
```

Phase 7 exists partly to convert this prediction into measured evidence.

## 9. First-principles latency prediction

The target clock is 100 MHz:

```text
Tclk = 10 ns
```

For the existing architecture, the predicted external transaction sequence is seven clock intervals from accepted start to externally visible done.

The exact naming of intermediate edges can vary depending on whether the launch edge is called cycle 0 or cycle 1, so the safest statement is based on **edge intervals**:

```text
accepted start edge
 -> launch/engine request
 -> memory latency / word pipeline
 -> word0 accumulation
 -> word1 accumulation
 -> word2 final-result registration
 -> requantizer product capture / controller capture-state entry
 -> activation capture / controller done-state entry
```

The prediction is therefore:

```text
latency = 7 clock periods
        = 7 * 10 ns
        = 70 ns
```

This must not yet be described as a measured integrated latency.

The purpose of the Phase-7 integration test will be to place timestamps or cycle counters on the accepted `start` and externally visible `done` and determine whether the measurement is exactly 70 ns.

If the measurement differs, the waveform—not the prediction—wins, and we must explain why.

## 10. Data path and control path must remain conceptually separate

A useful way to understand the integrated accelerator is to draw two parallel flows.

### Data path

```text
BRAM activation words ----\
                           -> unpack -> multiply -> reduce -> accumulate
BRAM weight words --------/                            |
                                                       v
                                                  INT32 result
                                                       |
                                                       v
                                              pipelined requantizer
                                                       |
                                                       v
                                                INT8 activation
```

### Control path

```text
external start
    |
    v
control FSM
    |
    +-> engine_start
    |
    +<- engine_done
    |
    +-> capture_activation
    |
    +-> busy
    |
    +-> external done
```

The control path does not calculate the convolution value. The data path does not decide when the complete external transaction is finished.

This separation will make later debugging much easier.

## 11. What the Phase-7 integration wrapper must eventually contain

We are not writing the RTL yet. Conceptually, the integration module will need these responsibilities:

1. Instantiate the supervisory `control_fsm`.
2. Instantiate the existing `memory_interface_dataflow` engine.
3. Connect `engine_start` to the engine's `start`.
4. Connect engine `done` back to the controller's `engine_done`.
5. Feed engine `result` to `requantize_relu_pipelined.acc_in`.
6. Provide the same `clk` and synchronous reset to all sequential blocks.
7. Add an architectural INT8 activation register.
8. Capture the requantizer output only when `capture_activation` is active.
9. Expose or connect the activation and weight memory interfaces.
10. Expose transaction-level `start`, `busy`, and `done`.

The design step will decide the exact module name, port list, parameter handling, reset behavior, and whether memory is instantiated internally or remains outside the integration wrapper.

---

## 12. Why we should not instantiate Basys-3-specific I/O yet

The original build order places convolution integration before the Basys 3 top-level.

That order is deliberate.

If board-specific switches, buttons, LEDs, debouncing, clock infrastructure, and pin constraints are introduced at the same time as the arithmetic integration, then a failing test has too many possible causes.

A cleaner sequence is:

```text
first:  pure synchronous NPU integration
then:   prove end-to-end functional behavior in simulation
then:   wrap the proven core for Basys 3 I/O
```

This is the same engineering principle used in larger ASIC/SoC projects: verify the reusable core before adding platform-specific shells.

## 13. Main integration failure modes to expect

Phase 7 should specifically guard against the following errors.

### Failure 1 — capturing q_out one cycle too early

If the activation register captures before the requantizer product register contains the final engine result, the output corresponds to an older accumulator value.

### Failure 2 — treating engine_done as combinational

The engine's `done` is registered. Assuming that the outer controller can react to a newly asserted `done` on the same clock edge creates an off-by-one-cycle error.

### Failure 3 — incorrect synchronous-memory assumption

If the integration testbench provides data with zero latency while the engine was designed for one-cycle latency, the test may pass for the wrong architecture or consume the wrong words.

### Failure 4 — incorrect packed-byte ordering

For the verified Phase-6 packing contract:

```text
lane 0 -> bits [7:0]
lane 1 -> bits [15:8]
lane 2 -> bits [23:16]
lane 3 -> bits [31:24]
```

Changing this ordering in the memory model silently changes the convolution.

### Failure 5 — allowing a new start while busy

The current controller contract accepts a transaction only when idle. A second start during `busy = 1` must not restart or corrupt the active transaction.

### Failure 6 — assuming unit timing closure guarantees integrated timing closure

The requantizer wrapper met 100 MHz individually. Integration adds routing, fanout, control, and other logic. Therefore the final integrated implementation must later receive its own synthesis and timing analysis.

## 14. What Phase 7 must prove

The integrated Phase-7 design will eventually need evidence for all of the following:

```text
1. one external start creates exactly one engine transaction
2. the expected three activation/weight words are requested in order
3. the 9-term signed INT8 convolution result is correct
4. engine_done is observed correctly by the outer controller
5. the final INT32 result enters the requantizer at the correct edge
6. the requantizer product stage is associated with the correct transaction
7. the final INT8 activation is captured on the correct edge
8. busy remains asserted for the complete transaction
9. done is exactly one cycle wide
10. reset returns all architectural state to a defined idle condition
11. predicted start-to-done cycle count is compared with measurement
12. no sample from a previous transaction leaks into the next transaction
```

A testbench that checks only the final output value would be insufficient because it could miss incorrect addresses, misplaced handshakes, or accidental extra cycles.

## 16. Core concept to retain

The central lesson of Phase 7 is:

> Correct modules do not automatically create a correct system. Integration correctness is mainly the correctness of **contracts across clock boundaries**: when data becomes valid, when it is sampled, when control pulses are observed, and which transaction each registered value belongs to.

For this NPU, the critical chain is:

```text
engine final result registered
    -> next edge: requantizer product registered
    -> next edge: INT8 activation captured
    -> controller reports transaction completion
```

Understanding that sequence is required before we design the integration RTL.
