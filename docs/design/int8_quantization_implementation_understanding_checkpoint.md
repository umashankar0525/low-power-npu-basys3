## 1. Why the requantization product needs 42 bits

**Status: PASSED**

The learner correctly restated the worst-case product calculation:

```text
acc_max   = 145161
M_int_max = 16777215

145161 × 16777215 = 2435397306615
```

and the power-of-two bound:

```text
2^41 < 2435397306615 < 2^42
```

Therefore the exact unsigned product requires 42 bits.

## 2. Why the post-ReLU accumulator magnitude uses 18 unsigned bits

**Status: NOT YET RESTATED**

The generated quantizer uses values in `[-127, +127]`.

For a 3×3 convolution:

```text
127 × 127 = 16129
9 × 16129 = 145161
```

After ReLU, only the non-negative magnitude is needed. Compare:

```text
2^17 = 131072
2^18 = 262144
```

Since:

```text
131072 < 145161 < 262144
```

17 unsigned bits are insufficient, while 18 unsigned bits are sufficient. This is why the RTL can use `acc_in[17:0]` under the stated Phase 6 bounded-data contract after confirming the accumulator is positive.

## 3. Why the Python reference must be independent of the RTL

**Status: NOT YET RESTATED**

The Python reference must calculate the expected arithmetic independently:

```text
INT8 activations + INT8 weights
        -> independent integer 3×3 convolution
        -> independent requantization
        -> expected INT8 output
```

If expected values were copied from, derived from, or generated by the RTL itself, the same implementation mistake could exist in both the DUT behavior and the expected result. That would allow a broken design to appear to pass.

An independent software reference can catch RTL errors in multiplication, accumulation, rounding, saturation, signed interpretation, or BRAM packing.
